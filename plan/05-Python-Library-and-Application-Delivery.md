# Part 5: Python Library and Application Delivery

## One engine, two ways to use it

The Python package and the web application should be two interfaces to the same planning engine. A researcher should be able to construct a scenario in Python, run it without opening a browser, inspect the intermediate quantities, and export the result. A web user should be able to make the same choices through a form and map and receive the same answer. The frontend should not maintain its own competing visibility or battery calculations. This is a proposed software architecture that follows the separation between model-based analysis and presentation, while the underlying scientific components are grounded in the papers identified throughout the plan. The TATC workflow paper supports reusable mission-analysis workflows, not this exact application stack. ([P01](06-Research-and-Source-Register.md#p01))

The package's purpose should be stated narrowly: **generate and explain finite-volume lunar data-delivery schedules under explicit geometry, radio, network, and energy assumptions**. The public documentation should not advertise a general lunar digital twin, flight-dynamics optimizer, navigation service, or landing-safety certification system. LunaNet includes positioning, navigation, and timing concepts, but a communications planner does not implement those services merely by citing LunaNet. Equally, a map of lunar terrain does not establish landing safety, thermal survival, radiation tolerance, or mechanical suitability. ([P09](06-Research-and-Source-Register.md#p09), [D06](06-Research-and-Source-Register.md#d06))

## The proposed package structure

The domain layer should define the meaning of a body, surface point, trajectory, terminal, ground station, data request, and hardware profile. A geometry layer should handle the selected kernels, frame transformations, positions, body occultation, and local directions. A terrain layer should own numerical DEM access and horizon profiles. Separate illumination and power layers should produce solar visibility, generation, and energy constraints. A links layer should transform opportunities into mode-specific usable contacts. Finally, a scheduling layer should allocate data, radio use, storage, and lander energy, with an exports layer translating immutable results into application and analysis formats. These are proposed module responsibilities, not claims that such modules already exist.

The core should depend on numerical and data-validation tools appropriate to the implementation, with SpiceyPy providing the Python interface to the chosen SPICE geometry. Raster access and coordinate transformations should remain body-aware; installing a geospatial package does not make its default Earth CRS correct for lunar data. A mixed-integer solver can be selected for the bounded resource-allocation problem after checking its license, installation footprint, and supported formulations. A small HTTP service, potentially built with FastAPI, is an implementation option rather than a research conclusion. The first release does not need a machine-learning model or a language model to determine physical feasibility. Its important decisions should remain inspectable numerical rules. ([P02](06-Research-and-Source-Register.md#p02), [P12](06-Research-and-Source-Register.md#p12), [P13](06-Research-and-Source-Register.md#p13))

## A scenario contract that prevents hidden assumptions

A scenario should identify a unique run version, a lander location and frame, panel and antenna heights, data-ready time, data volume with an unambiguous unit, delivery deadline, and analysis horizon. It should reference a hardware profile with panel configuration, battery capacity, initial energy, reserve, base load, charge/discharge limits, and radio modes. It should also identify the allowed relay trajectories, terminal capabilities, station coordinates, service calendars, storage limits, and route families. The scenario should record whether rates are assumed or obtained from a link budget, whether pointing is idealized, and whether the relay availability is a synthetic service assumption. Missing fields must not silently become unlimited storage, continuous service, zero base load, or perfect pointing.

A good initial Python interface would expose a high-level operation such as `plan_delivery(scenario)` and lower-level operations for horizon generation, illumination, contact generation, and schedule validation. These names are proposed API contracts, not runnable examples of an existing package. The high-level result should contain both the final answer and references to the intermediate records needed to explain it. A user should be able to inspect why a contact failed, rerun a scenario with a different battery reserve, or compare two sites without copying internal geometry code into a notebook. Inputs should be immutable during a run so a frontend edit cannot alter a calculation already in progress.

The state schema should require position units, frame, origin, epoch, and time scale. The contact schema should include sender, receiver, a required timing-convention enum fixed to source-transmit epochs for native SOMA contacts, the one-way-delay model, payload-rate definition, available capacity, terminal identifiers, mode identifier, service provenance, and quality flags. An importer using another endpoint convention must convert explicitly. Every exported allocation should connect its data chunk to a specific contact and provide the source transmit interval, derived receiver-occupancy interval, and the timestamp when the received chunk becomes available for forwarding. Receiver service and radio restrictions must be checked against the arrival interval, not the source interval. The result should distinguish `feasible_under_assumptions`, `infeasible_in_model`, and `unknown`, with separate fields for solver status and physical-model fidelity. For example, a mathematically valid schedule using assumed rates remains an assumed-rate simulation; the word “feasible” must not erase that qualification. ([P11](06-Research-and-Source-Register.md#p11), [P12](06-Research-and-Source-Register.md#p12), [D07](06-Research-and-Source-Register.md#d07))

## The complete calculation pipeline

A run should first validate all inputs and confirm kernel and terrain coverage. It should then resolve the physical lander position, load or compute horizon profiles, generate time-tagged states, and calculate Sun and endpoint directions. From these, it builds geometric opportunity intervals and applies the terminal, service, and link-budget rules. In parallel, it calculates the lander's available solar generation and fixed demand on the common timeline. The scheduler uses those quantities to search the allowed route families and produces a candidate allocation. A separate validator then replays the allocation to check byte conservation, causality, capacity, storage, radio conflicts, energy, and the final arrival deadline. Only a candidate that passes this replay should be returned as a feasible schedule. ([P02](06-Research-and-Source-Register.md#p02), [P05](06-Research-and-Source-Register.md#p05), [P06](06-Research-and-Source-Register.md#p06), [P13](06-Research-and-Source-Register.md#p13))

Contact boundaries deserve more care than a coarse animation timestep. The engine should initially sample geometry, identify changes of state, and refine event boundaries where a visibility or link-margin condition crosses its threshold. It should test for missed short opportunities by reducing the sampling step and comparing resulting intervals, rather than assuming a sign change between widely spaced samples catches every event. The optimizer's time bins can then align with contact, rate, service, and relevant energy events. Raster resolution, geometry sampling, and scheduling resolution are three different sources of approximation and should be reported separately. A smooth display should never be described as evidence of a fine scientific timestep.

Caching should target expensive deterministic inputs, especially terrain horizons and ephemeris samples. The key must include the relevant source versions and parameters so a changed antenna height, kernel set, or DEM cannot reuse an incompatible result. Analysis jobs should be isolated sufficiently that one run's kernel configuration or temporary data cannot contaminate another. Large numerical files should be prepared or windowed for the selected region instead of forcing every browser request to download an entire polar mosaic. Performance targets should be measured on named hardware and realistic scenarios after implementation; this plan makes no claim that the full pipeline already runs in real time.

## How the browser and service communicate

The frontend should submit a complete scenario and receive a job identifier. It should then display progress through meaningful stages such as input validation, horizon preparation, contact construction, and scheduling. A finished job should return a result manifest and the visualization data needed for the map and timeline. Canceling a job should stop avoidable computation and preserve a clear canceled status, not leave a partially filled “success” card. If a user changes the site while an earlier job is finishing, the application should match results to the scenario hash and avoid replacing the new scenario with stale data.

The map should use a derived display payload, such as CZML or sampled entity data, rather than the full numerical workload. The scientific arrays can retain the detail needed for verification while the visual samples are reduced to a level appropriate for the browser. That reduction must not shift the selected transmission intervals or recompute the final metrics. A text schedule should remain available if the map cannot load. This separation makes Cesium an inspectable client of the engine rather than a hidden source of scientific state. ([D05](06-Research-and-Source-Register.md#d05), [D11](06-Research-and-Source-Register.md#d11))

## What the eventual planner should export

Each completed analysis should be exportable as a self-contained run package. Its scenario file should reproduce the request, its manifest should identify every data and software dependency, and its contact and schedule files should expose both available opportunities and chosen allocations. Separate energy and buffer histories should make resource use auditable. A display file can reproduce the map animation, while a short Markdown explanation should state the outcome, policy, assumptions, warnings, and limitations. These are proposed outputs of the future application, not files claiming that a simulation has been run in this project-plan folder.

A practical export set would include scenario JSON, a run manifest, contacts CSV, schedule CSV, energy CSV, buffer-history CSV, summary JSON, display CZML, and a human-readable explanation. The CSV headers should name units explicitly, and unknown values should remain distinguishable from zero. A station availability source should distinguish a synthetic calendar from an operator-provided one. The package should include source URLs and checksums rather than redistributing restricted tiles, papers, or large kernels without checking their terms. Reproducibility requires knowing which data were used; it does not require pretending every source can legally be bundled.

## A development sequence with concrete exit conditions

The first milestone should lock down the scenario contract and a small reproducible dataset bundle. Select a few sites inside verified terrain coverage, a bounded time interval supported by the chosen kernels, one lander profile, and a small relay and ground-network preset. Record which inputs are measured, published, synthetic, or assumed. This milestone ends when the same scenario can be loaded from a file without any implicit browser state and when unsupported dates or coordinates produce explicit errors. It should not end with a polished globe that has no agreed physical interpretation.

The second milestone should implement geometry and terrain independently of the website. A command-line or notebook run should produce the local Sun/Earth directions, range histories, terrain horizons, and geometric contact intervals, with unit and frame tests. Compare selected results against a separately implemented calculation or authoritative service using matching definitions. Horizons and SPICE may share JPL ephemeris information, so agreement can validate transformation and implementation choices without independently proving the ephemeris itself. This milestone ends with documented numerical checks, not a claim of operational navigation accuracy. ([P02](06-Research-and-Source-Register.md#p02), [P03](06-Research-and-Source-Register.md#p03), [P05](06-Research-and-Source-Register.md#p05))

The third milestone should add link profiles and a deliberately simple scheduler. First solve synthetic contact schedules whose answers can be calculated by hand, including the example in Part 3. Then run direct-to-Earth and single-relay cases using generated geometry. Assumed-rate cases should remain visibly distinct from link-budget cases. Add storage and radio conflicts before attempting a more complex network. This milestone ends when a replay validator can reject an intentionally corrupted schedule and when the optimizer reports feasible, infeasible, and unresolved cases honestly. ([P11](06-Research-and-Source-Register.md#p11), [P12](06-Research-and-Source-Register.md#p12), [P13](06-Research-and-Source-Register.md#p13))

The fourth milestone should integrate the solar-generation and battery model into scheduling. Begin with a constant-load synthetic case, then add shadows and radio activity. Verify charge saturation, efficiency losses, reserve limits, discharge-power limits, and the distinction between radiated and electrical power. The output should explain a case where geometry permits a transfer but energy prevents it. This milestone ends only when energy changes the chosen allocation through a constraint, not merely through a warning calculated afterward. The lunar-instrument power study gives the methodological precedent, but the chosen SOMA profile still needs its own validation. ([P06](06-Research-and-Source-Register.md#p06))

The fifth milestone should connect the verified engine to the Cesium interface, timeline, controlled site/date comparison, and export action. Use the current official Moon configuration and test the coordinate bridge. Only after that vertical slice is reliable should the team add an optional Earth-orbit route, additional hardware profiles, or richer optimization policies. These are milestone gates rather than a promised calendar: development duration depends on the team, the desired physical fidelity, and whether suitable trajectory and hardware data are available. For a hackathon, the defensible reduced version is a few curated scenarios with openly identified precomputed geometry and a genuine reschedulable transfer problem, not an unvalidated claim of arbitrary global mission planning.

## Verification that matches the scientific claims

Testing should occur at several levels. Numerical unit tests should cover coordinates, units, time conversions, horizon construction, illumination fractions, rate integration, and battery updates. Analytic or hand-computable cases should check geometry on a simple sphere and transfers through a tiny contact network. Research comparisons should match the paper's dates, heights, terrain, and definitions before comparing metrics. Integration tests should replay an entire exported schedule and prove that no data was duplicated, sent before it existed, or delivered after a reported deadline. User-interface tests should confirm that displayed states and timestamps match the stored result. None of these levels is a substitute for the others.

The schedule replay should be independent of the optimizer's internal bookkeeping where practical. It should recompute occupied intervals, confirm each allocation lies inside the applicable usable contact, integrate enough payload capacity, verify the required buffer is available, and check terminal conflicts at both endpoints. It should trace lander energy through the complete modeled interval, including waiting periods and base demand. A result that consumes more energy than the profile permits should fail validation even if an optimizer incorrectly labeled it feasible. Tiny cases can also be exhaustively enumerated to check the optimization formulation itself.

Sensitivity testing should show how the result changes when terrain margins, initial battery energy, radio rate, service availability, or numerical resolution changes. This is different from assigning a probability of mission success. A robust result under several stated perturbations is useful evidence, but a confidence percentage requires justified statistical models. Report unresolved differences and model exclusions alongside the schedule. The contribution worth demonstrating is that SOMA produces a reproducible answer and makes its dependencies visible, not that it removes uncertainty from lunar mission design. ([P05](06-Research-and-Source-Register.md#p05))

## The demonstration and the final boundary

The demonstration should tell one short story. Start with a lander, a dataset, and a deadline. Show a direct-to-Earth plan if it is feasible. Change the site or date under a controlled rule so the direct route no longer has enough usable capacity or energy. Enable the preset lunar relay and show the resulting transfer, storage, and forwarding sequence, or explain why even that route fails. Then export the exact scenario and schedule. The chosen demonstrations should be selected from actual computed results once the engine exists; the team must not invent favorable mission outcomes to fit this narrative.

Success means a user can answer “what should transmit when, through whom, and under which assumptions?” and another person can reproduce that answer from the exported inputs. It does not mean SOMA has booked ground time, implemented a flight DTN stack, certified a relay constellation, proven thermal survival, or found the best landing site for every mission objective. A focused planner with a trustworthy boundary is a stronger project than a broad simulator whose graphics imply more validation than its models have received.
