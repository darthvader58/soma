# Part 1: Lunar TATC and the Analysis Foundation

## What TATC contributes

The useful idea behind TATC is to represent a mission as explicit objects and reusable calculations rather than as a single hard-coded simulation. A spacecraft has a state history, an instrument or antenna has constraints, a surface location is an analysis target, and a time interval defines the study. Those ingredients can be combined to ask when assets can observe or communicate and how alternatives differ. The research lineage concerns early-stage mission and constellation analysis; the current Python repository describes its scope specifically as Earth-observing mission concept studies. That is a valuable starting point for SOMA's architecture, but it is not evidence that the existing package already solves lunar communications planning. ([TATC research, P01](06-Research-and-Source-Register.md#p01); [current implementation, D02](06-Research-and-Source-Register.md#d02))

The recommendation is to build a small companion package, provisionally called **soma_lunar**, rather than immediately fork TATC or change its global constants. The companion would adopt the useful separation between schemas, state generation, analysis, and outputs. It could adapt suitable algorithms with attribution, but it would own the lunar coordinate model, the ephemeris interface, contact feasibility, illumination, scheduling, and the export contract. This is an engineering recommendation based on the audited coupling in the current code, not a claim that a paper has established this exact package architecture as optimal. It preserves existing Earth behavior and makes a later upstream generalization easier to review.

## Why changing the radius is insufficient

At the audited revision, the general-perturbations orbit interface returns Earth-centered Skyfield states and offers explicit WGS84 geographic conversions. The geometry utilities construct a WGS84 geodesic object, and the ground-station schema is described in WGS84 terms. Solar quantities in inspected analysis functions are calculated relative to Earth and the Sun. These are not incidental names: they determine coordinate transformations, the surface underneath an observer, and the relationship between an orbit and the rotating body. Feeding lunar coordinates into these paths would not become correct merely because a visualization used a smaller sphere. ([D02](06-Research-and-Source-Register.md#d02))

The terrain-mask implementation is a particularly instructive example. It already exposes an effective-Earth-radius factor, with a value of one available for straight-line geometry rather than the atmospheric four-thirds-Earth approximation. However, its search-window calculation still uses Earth's mean radius, its sampling uses Earth geodesics, and the elevation-angle utility multiplies the supplied factor by Earth's radius. Setting the factor to one is therefore not a lunar conversion. SOMA needs Moon-specific coordinates and curvature, and it should not assume terrestrial refraction on the Moon. It should also replace the existing mask's permissive missing-data behavior: the inspected implementation can report minus 90 degrees where no valid terrain sample exists. SOMA should report an unknown horizon instead of interpreting missing lunar data as an unobstructed view. ([D02](06-Research-and-Source-Register.md#d02); [challenge's no-atmospheric-refraction requirement, D01](06-Research-and-Source-Register.md#d01))

The audit does not justify saying that TATC has no relationship to SPICE. Its dependencies already include SpiceyPy, and it bundles a DE421 planetary ephemeris kernel. The narrower, defensible finding is that the inspected orbit and analysis APIs are not a general lunar-SPICE state provider. A dependency can be present without the required body-aware interfaces being implemented. SOMA should reuse compatible infrastructure where possible, while testing the actual interface it intends to call rather than reasoning from a package name. ([D02](06-Research-and-Source-Register.md#d02))

## The geometry engine and its research basis

SPICE is the recommended foundation for positions, orientations, and time conversions. In simple terms, SPICE reads carefully identified data files and answers questions such as where Earth is relative to the Moon, how the Moon is oriented at a particular instant, and how a vector should be expressed in a selected reference frame. The foundational SPICE papers describe this geometry-information system and its mission-analysis role. They support using a consistent kernel-based geometry layer; they do not supply a fictional relay's orbit, automatically solve communications, or certify the accuracy of every input file. ([Acton and colleagues, P02](06-Research-and-Source-Register.md#p02))

The first implementation should keep two kinds of coordinates explicit. A Moon-centered inertial frame is convenient for spacecraft motion, while a Moon-fixed frame rotates with the terrain and is convenient for a stationary lander. Earth ground stations require an Earth-fixed representation before they are transformed into the common geometry used for a link. Every state must identify its origin, orientation frame, epoch, time scale, and units. A vector from the lunar center is different from a vector from Earth's center even when both use axes labeled J2000. Transforming orientation without translating the origin is a serious error, not a harmless display offset. The SPICE system's frame and ephemeris documentation provides the implementation rules for those distinctions. ([P02](06-Research-and-Source-Register.md#p02), [D03](06-Research-and-Source-Register.md#d03))

For the initial terrain-backed demonstration, use a deliberately consistent DE421-related lunar setup because the selected high-resolution LOLA product identifies its reference frame as the mean-Earth frame of DE421. Record the explicit frame realization rather than only the generic alias MOON_ME. A matched lunar frame kernel, lunar orientation kernel, planetary ephemeris, and leap-second kernel should be selected together, with their actual time coverage checked before a run. An upgrade to DE440 is reasonable, but it must include the documented transformation and a registration test against the terrain. NAIF's DE440 frame kernel states that its mean-Earth realization is closely aligned with DE421's, not mathematically identical. It also documents much larger distinctions between principal-axis, mean-Earth, and simplified IAU lunar frames. Those distinctions matter when the map and DEM contain meter-scale features. ([D03](06-Research-and-Source-Register.md#d03), [D04](06-Research-and-Source-Register.md#d04))

## Surface points, heights, and time

A surface point should contain planetocentric latitude, east-positive longitude under a declared wrapping convention, its Moon-fixed frame, and the reference surface from which elevation is measured. For a spherical lunar reference, its Cartesian location can be computed from latitude, longitude, and the reference radius plus elevation. That conversion must not silently use an Earth ellipsoid. The high-resolution LOLA maps and associated polar products provide their coordinate and reference-radius conventions; SOMA must preserve them in a dataset manifest rather than infer them from a GeoTIFF filename. The array height above the local ground and the antenna height above ground should be separate quantities because they can see different horizons. ([P04](06-Research-and-Source-Register.md#p04), [P05](06-Research-and-Source-Register.md#p05), [D04](06-Research-and-Source-Register.md#d04))

The application should accept timezone-qualified UTC timestamps and pass them through one time-conversion layer. Internal geometry may use SPICE ephemeris time, but exported timestamps must remain understandable and reproducible. There should be no silent conversion between browser-local time, UTC, and an arbitrary lunar clock. In particular, an inherited **solar_hour** field based on timestamp-plus-longitude arithmetic is not a substitute for lunar Sun geometry. If such a field remains in an Earth-oriented diagnostic adapter, keep it labeled as that arithmetic convenience and outside the lunar illumination calculation. Actual solar direction should come from the chosen ephemeris, observer position, and reference-frame transformation. ([P02](06-Research-and-Source-Register.md#p02), [P03](06-Research-and-Source-Register.md#p03))

## What should count as a relay trajectory

The preferred production input is a state history with explicit provenance, such as an appropriate SPICE spacecraft kernel or a documented ephemeris file. A CCSDS Orbit Ephemeris Message is a useful interchange option because it carries trajectory metadata and time-tagged states, but merely accepting its extension does not make an importer complete. The parser must check center, reference frame, time system, units, coverage, interpolation instructions, and any gaps. Files with unsupported conventions should be rejected with a precise error. Generic planetary kernels provide the Earth, Moon, and Sun geometry; they do not automatically include every operational relay spacecraft. ([P02](06-Research-and-Source-Register.md#p02), [D08](06-Research-and-Source-Register.md#d08))

For the first demonstration, synthetic lunar relay trajectories are acceptable if prominently labeled. A short-arc two-body lunar orbit can be useful for a software test, but it should be called a synthetic two-body preset, not an operational ephemeris or a validated frozen orbit. An Earth-Moon libration-point orbit cannot be obtained by drawing a Keplerian ellipse around the Moon. The Queqiao-2 system paper and the Lunar Data Network preliminary design paper illustrate that operationally useful lunar relay orbits involve mission-specific choices and dynamics. SOMA should initially consume a bounded preset trajectory instead of claiming to solve that separate design problem. ([P07](06-Research-and-Source-Register.md#p07), [P08](06-Research-and-Source-Register.md#p08))

## A terrain service, not a screenshot service

The library should load numerical elevation data independently of the map renderer. At each selected site, it can precompute a horizon profile: the highest terrain elevation angle in each azimuth direction as seen from a specified observer height. The research-backed advantage is that the expensive terrain calculation can be reused while the Sun, Earth, and relay directions change with time. This follows the horizon-method literature rather than inventing a new shadow model. Make the distinction an interface rule: directional horizon profiles may classify the Sun and other justified far-field approximations, while every finite spacecraft link must use a segment-limited terrain and body-shape test through the target range. A distant ridge beyond a nearby spacecraft must not block the link. Include a regression test with an otherwise visible nearby relay and terrain beyond it, so the implementation cannot accidentally substitute an infinite-distance skyline. ([P03](06-Research-and-Source-Register.md#p03), [P05](06-Research-and-Source-Register.md#p05))

A practical implementation should combine detailed nearby terrain with coarser distant terrain and increase the search extent until the relevant horizon is stable under a declared convergence test. It must not infer that the boundary of a small high-resolution tile is the boundary of possible obstructions. Barker and colleagues explicitly discuss near-field and far-field contributions to the horizon and the effect of terrain-height uncertainty. SOMA can adopt that separation while retaining its own measured resolution and convergence limits. The cache key should therefore include site coordinates, observer height, source DEM hashes, reference frame, sampling parameters, and algorithm version. A cached horizon for a different antenna height is a different physical calculation. ([P05](06-Research-and-Source-Register.md#p05))

## Reproducibility and the completion gate

Every run should retain a compact manifest identifying the library version, TATC adapter revision if used, kernel files and checksums, DEM product and revision, hardware presets, station availability assumptions, numerical sampling settings, and solver status. Results should be reproducible without remembering which browser tab happened to be open. A coordinate round-trip test, a known lunar landmark registration test, a unit test that distinguishes kilometers from meters, and comparisons against an independent SPICE/Horizons calculation should pass before the communications scheduler is trusted. These are proposed verification procedures, not completed validation results. Agreement between two calls to the same underlying function is a useful regression test but not independent scientific validation.

The current TATC license is BSD 3-Clause, so adapted or redistributed code must retain the required copyright notice, conditions, and disclaimer. A companion package should make copied or adapted portions identifiable and separately review dependency and data terms. The project's name and research citations must not imply NASA endorsement. The foundation is complete only when it can produce documented, body-consistent states and terrain-aware directions through a Python interface, without relying on Cesium to decide the physics. ([D02](06-Research-and-Source-Register.md#d02))
